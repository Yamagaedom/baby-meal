# 주간 식단 계획·영양 체크·음식 재고 기능 검토

작성일: 2026-11-01 · 상태: 구현 제안, 앱·DB 미변경

## 1. 권장 방향과 현재 기반

주간 식단을 **집에서 먹을 끼니를 정하고, 준비할 음식과 분량을 결정하는 기능**으로 추가한다. 사용 흐름은 `짧은 문답 → 7일 식단 초안 → 메뉴·조리량 조정 → 확정 → 조리·재고 등록 → 먹은 기록`이다.

| 현재 확인한 코드 | 재사용할 부분 | 추가할 부분 |
|---|---|---|
| `src/features/recommend/index.ts`, `personalization.ts` | 월령·간 단계·알레르기 필터, 선호도, 최근 섭취 메뉴 고려 | 여러 날짜의 구성, 반복·조리 일정·재고·영양을 함께 고려하는 배치 로직 |
| `src/features/ingredient-search/index.ts` | 선택 재료 매칭, 부족한 재료 표시 | 주간 재료 활용도와 장보기 합산 |
| `src/features/serving/index.ts` | 레시피 기준 대비 1~5회분 재료 계산 | 계획에 먹을 양과 조리할 양을 각각 저장 |
| `src/features/pantry/index.ts`, `PantryItem` | 보유 식재료 목록 | 완성 음식의 조리별 재고, 잔여 회분, 예약량, 입출고 이력 |
| `src/features/meal-log/index.ts`, `MealLog` | 먹은 날짜·끼니·평가·섭취 정도·반응 기록 | 계획·재고 출고와 연결, 중복 차감 방지 |
| `Ingredient`, `Recipe` | 재료 분류·분량, 나트륨 값 | 다른 영양소, 공식 식품 코드, 영양 데이터 출처·버전·누락 여부 |

기존 PRD의 REC-07은 주간 식단표·장보기 목록을 P2로 두고 있다. 이번 제안은 이 범위를 구체화하고, 음식 재고·영양 추정 기능을 추가하는 변경이다. 의료·영양 상담은 제공하지 않는다는 기존 범위는 유지한다.

## 2. 진입점과 화면 배치

### 주 메뉴

최종 권장 메뉴는 **홈 / 레시피 / 식단 / 기록 / 마이**다. 모바일에서 여섯 번째 탭을 추가하지 않고, 기존 `재료로 찾기`를 레시피 안의 `전체 / 재료로 찾기 / 즐겨찾기`로 묶는다. `/ingredients` 주소와 홈의 재료 검색 바로가기는 유지하고, 해당 경로에서는 레시피 메뉴가 활성화되도록 한다.

| 진입점 | 행동 | 전달할 문맥 |
|---|---|---|
| 홈, 식단이 없을 때 | `이번 주 식단 짜기` | 현재 아기, 저장된 이전 선호 설정 |
| 홈, 확정한 식단이 있을 때 | 오늘 계획을 보여주고 `주간 식단 보기` | 오늘 날짜·현재 아기; 오늘 계획을 일반 추천보다 먼저 표시 |
| 재료 선택 결과 | `이 재료로 일주일 구성` | 지금 선택한 재료를 그대로 전달, 재입력 없음 |
| 레시피 상세 | `식단에 담기` | 날짜·끼니 선택 후 초안에 추가 |
| 식단 메뉴 | `이번 주 / 만든 음식` | 식단과 식사·간식 재고를 왕복 |
| 조리 완료 | `만든 음식 저장` | 실제 만든 회분·보관 장소·날짜 확인 |

주간 식단 화면 상단에는 아기, 기간, `조건 수정`을 둔다. 본문은 식단, 접힌 `영양 체크`, `준비할 음식·장보기` 순서다. 모바일은 7일 선택 막대와 선택한 하루의 끼니 목록으로 구성하고, `한 주 모아보기`에서 요일별 목록을 제공한다. 데스크톱에서는 주간 표를 사용할 수 있다.

각 끼니에는 메뉴, 먹을 예정 회분, `만들 예정` 또는 `냉동 재고 사용`, `바꾸기`, `유지`를 표시한다. `유지`한 메뉴는 전체 재추천에서도 보존한다. 날짜 이동은 버튼/날짜 선택으로 가능하게 하고 드래그는 선택 기능으로 둔다.

## 3. 문답: 3개 화면, 짧은 질문 5개

긴 채팅을 기본 UI로 사용하지 않는다. 선택 칩과 미리 채운 값으로 구성하고, 답변은 한 화면 요약에서 바로 수정할 수 있게 한다. 첫 사용은 약 1분 안에 초안을 보는 것을 제품 목표로 삼고, 실제 사용자 확인 전 달성했다고 표시하지 않는다.

월령·간 단계·알레르기는 기존 프로필을 적용하고 다시 묻지 않는다. 상단의 `적용 중인 조건`에서 확인·수정할 수 있다. 알레르기 제외는 문답에서 해제할 수 없다.

| 화면 | 질문 | 간결한 답변 방식 | 기본 동작 |
|---|---|---|---|
| 1. 먹을 일정 | ① 어떤 끼니를 준비할까요? | `매일 세 끼 / 평일 아침·저녁, 주말 세 끼 / 직접 선택` | 시작일과 7일 기간 표시. 특정 생활패턴을 묵시적으로 가정하지 않고 선택하게 함 |
| 1. 먹을 일정 | ② 간식도 넣을까요? | `없음 / 하루 1번 / 하루 2번` | 초기 제안은 하루 1번, 변경 가능. 건강 권장 횟수가 아닌 일정 선택 |
| 2. 사용할 재료 | ③ 먼저 쓸 재료가 있나요? | 선택 재료 칩, `냉장고에서 가져오기`, `없어요` | 재료 화면에서 왔다면 자동 입력. 만든 음식 재고도 요약하고 사용 여부를 수정 가능 |
| 3. 준비 방식 | ④ 어떻게 준비하고 싶나요? | `매일 간단히 / 주 2회 모아서 / 상관없어요` | 매일 간단히는 조리시간 선호, 모아서 준비는 조리 요일 2개를 이어서 선택. 제안값은 수정 가능 |
| 3. 준비 방식 | ⑤ 이번 주에 더 중요한 것은? | 최대 2개: `재료 소진 / 조리 간편 / 좋아하는 메뉴 / 다양한 메뉴` | 선택 재료가 있으면 재료 소진·조리 간편, 없으면 조리 간편·다양한 메뉴를 제안 |

추가 조건은 `더 설정하기`로 접는다: 추가 장보기 허용 여부, 보유 도구, 꼭 피할 재료, 조리시간 상한, 같은 메뉴 반복 선호, 날짜별 외식·어린이집 일정. 기피 재료는 알레르기와 다른 선호 설정으로 저장한다.

추가 재료 기본값은 `필요하면 추가`로 명시하고, `선택한 재료만`도 제공한다. 실제 재고 수량은 모르면 입력하지 않아도 되며, 이 경우 재료 보유 여부만 추천에 반영한다. 다음 주에는 `지난번 조건으로 만들기`와 변경된 재고 요약을 보여주고 다섯 질문을 반복하지 않는다.

초안 하단에 `선택 재료 4종 활용 · 추가 재료 3종 · 조리 예정 2일`처럼 실제 계산값을 요약한다. 이 숫자는 예시이며 최종 화면에서 고정값으로 쓰지 않는다.

## 4. 식단 구성 로직

주간 구성은 기존 레시피를 조합하는 서버 로직으로 구현한다. 21끼 이상의 새 레시피를 AI로 일괄 생성하지 않는다. 기존 일일 AI 생성 한도와 분리하고, 새 레시피 생성은 사용자가 명시적으로 선택할 때만 기존 절차로 수행한다.

1. **입력 정규화:** 현재 아기, KST 기준 시작일, 연속 7일, 필요한 끼니·간식, 선택 재료, 조리일·선호를 저장한다. 어린이집·외식은 `외부 식사`, 필요 없는 끼니는 `계획 제외`로 구분한다.
2. **후보 제한:** ACTIVE 상태에 더해 월령·알레르기·간 단계·명시적 제외 조건·출처 확인 정책을 통과한 후보만 사용한다. 보관 기한이 예정 식사일보다 빠른 음식 재고는 배치하지 않는다.
3. **선호 반영:** 사용 가능한 음식 재고와 먼저 소진할 재료, 선택 재료 활용률, 추가 재료 수, 조리 부담, 먹은 기록·즐겨찾기, 메뉴 다양성 순위를 설정에 맞게 계산한다. 안전 조건은 점수로 상쇄하지 않는다.
4. **한 주 조합:** 식품군 편중과 같은 메뉴 연속 배치를 줄이면서 조리일·재고 수량을 만족하는 조합을 탐색한다. 하루 추천 함수를 일곱 번 실행하는 방식은 반복과 재고 중복을 관리할 수 없어 사용하지 않는다. 작은 후보 집합에서 단계별 후보 탐색과 부분 교체로 시작한다.
5. **영양 계산:** 각 끼니의 제공량 기준으로 재계산한다. 수치 비교가 가능한 항목은 조합 선택에도 활용하고, 데이터가 없는 항목은 평가 보류로 남긴다.
6. **부족한 조건 설명:** 후보 부족 시 빈 끼니와 사유를 반환하고 `추가 재료 허용 / 조리시간 늘리기 / 직접 담기` 등을 제안한다. 알레르기나 월령 제한을 자동 완화하지 않는다.

재료 매칭은 사용자가 선택한 재료 자체의 활용률과 레시피 필수 재료의 보유율을 함께 본다. 양념만 일치한 메뉴가 높은 순위를 받지 않도록 한다. 재료가 없으면 선호도·다양성·조리 편의 중심으로 구성한다.

현재 재료 매칭의 재료군 확장은 검색 보조에만 재사용한다. 예를 들어 생쌀과 지은 밥을 수량·영양 계산에서 동일한 무게로 취급하지 않는다. 대체재를 실제 사용하면 대체한 재료와 분량으로 영양·알레르기를 다시 계산한다.

레시피에 `한그릇 / 밥·주식 / 반찬 / 간식` 역할을 추가하고, 한 끼에 여러 항목을 담을 수 있게 한다. 반찬 하나를 완전한 한 끼로 간주하지 않는다. 밥·과일·우유 등 단순 음식은 검증된 식품 항목과 양으로 추가할 수 있게 한다. 이 항목들도 알레르기·영양 계산 대상이다.

### 출처 점검 결과를 반영한 출시 조건

앞선 DB 점검에서 샘플 유튜브 ID와 모의 식품안전나라 링크가 확인됐다. 현재 ACTIVE·높은 qualityScore/trustScore만으로 자동 주간 식단 후보를 인정하면 문제가 반복된다.

- 생성 단계에서 가상 출처 저장을 막고 기존 자료의 출처 상태를 재분류하는 작업을 먼저 진행한다.
- 링크 응답 성공 여부와 레시피 근거 관련성을 별도로 확인한다. HTTP 200만으로 출처 확인 완료가 되지 않는다.
- `sourceVerificationStatus`, `verifiedAt`, 확인 방법·근거를 저장한다. 기존 데이터의 초기 상태는 미확인으로 둔다.
- 영양 계산의 근거는 레시피 참고 링크와 별도로 관리한다. 출처 링크가 확인돼도 모든 영양소가 검증된 것은 아니다.
- 후보가 부족하면 일부 초안과 이유를 보여준다. 출처 미확인 레시피를 자동으로 보충해 완성된 주간 추천처럼 보이지 않게 한다.

## 5. 영양 체크

현재 스키마의 정량 영양 정보는 나트륨 중심이다. 재료 종류만 보고 단백질·철·칼슘이 충분하다고 판정할 수 없다. **식품군 구성 확인과 영양소 추정치를 함께 제공하되, 각각 확인 가능한 범위를 표시한다.**

### 표시와 계산

| 구분 | 제공할 정보 | 데이터가 부족할 때 |
|---|---|---|
| 식품군 구성 | 곡류, 단백질 식품, 채소·과일, 유제품 등 실제 포함 항목과 주간 분포 | 식품군 구성만 보여주며 영양소 충족으로 표현하지 않음 |
| 핵심 영양소 | 열량, 탄수화물·단백질·지방, 철, 칼슘, 나트륨부터 추정 | 항목별 `일부 계산 / 계산 불가`, 누락 재료 표시 |
| 확장 영양소 | 식이섬유·비타민 D 등 확보한 공식 데이터에 따라 추가 | 없다는 이유로 0으로 처리하지 않음 |
| 기준 비교 | 해당 연령의 적용 가능한 섭취기준과 비교, 기준 종류·출처 표시 | 필요한 입력·음식 정보가 없으면 충족률이나 부족 판정 생략 |

일일 상세와 주간 분포를 모두 제공한다. 기본 화면은 `채소가 포함된 식사가 적어요`처럼 근거가 있는 제안과 `메뉴 바꾸기`를 연결한다. 모든 필수 영양소를 충족한다는 단일 점수·완료 배지는 제공하지 않는다.

**데이터 흐름:** 공식 식품 코드 매핑 → 실제 사용 재료의 가식부 중량·생/조리 상태·단위 정규화 → 레시피 총량 추정 → 기준 회분으로 나눔 → 끼니별 제공 회분을 곱함 → 하루·주간 합산.

조리 후 중량·수율·영양소 보존 계수는 근거가 있는 경우에만 적용한다. 자료가 없으면 재료 기반 추정임을 표시한다. `약간`, null 분량, 정체불명 대체재는 정확한 수치로 바꾸지 않는다. 영양소별 누락과 계산 가능 비율을 저장하고, 불완전한 합계를 완전한 섭취량처럼 비교하지 않는다.

외부 식사·우유·추가 간식이 빠진 상태에서는 `앱에 계획한 음식 기준`으로 표시하고 하루 전체의 부족을 판정하지 않는다. 계획량과 실제 먹은 양도 따로 표시한다. 현재 `다 먹음/반/조금` 기록은 정밀 섭취량이 아니므로 실제 영양값은 추정 또는 미산출로 남긴다.

식품 함량은 식약처 [K-FIND 식품영양성분 DB](https://various.foodsafetykorea.go.kr/nutrient/)의 다운로드/API를 사용해 식품 코드·출처·버전을 함께 저장하는 방향을 권장한다. 기준값은 한국영양학회의 [2025 한국인 영양소 섭취기준 공개자료·정오표 안내](https://www.kns.or.kr/fileroom/FileRoom_view.asP?BoardID=Kdr&Page=1&cnsearch=&idx=167&mode=mod&restring=96252FFileRoom96252FFileRoom%252EasP96253Fxsearch%253D0%253D%253Dxrow%253D10%253D%253DBoardID%253DKdr%253D%253DPage%253D1&xsearch=1)를 기준으로 도입 시 원문·정오표를 대조한다. 기존 PRD의 2020년 예시 숫자는 그대로 사용하지 않는다.

영양 기준의 연령 구간을 앱의 조리 단계와 동일하게 취급하지 않는다. 기준 종류(권장섭취량·충분섭취량·상한섭취량 등)의 의미도 구분한다. 이 검토에서는 특정 영양소의 목표 숫자를 확정하지 않았으며, 식품 매핑과 연령별 정책 확인을 정량 영양 체크 출시 조건으로 둔다.

## 6. 레시피별 만들 양과 장보기

**먹을 양과 만들 양을 별도 입력·저장한다.** 날짜별 식단 카드에서는 먹을 예정 회분, `준비할 음식` 목록에서는 각 레시피·조리일별 만들 회분을 조절한다. 기존 1~5회분 스테퍼를 재사용하고 더 필요하면 조리 묶음을 추가한다.

예: 두부전이 월·수·금에 각 1회분 예정이면 필요한 양은 3회분이다. 사용자가 4회분을 만들기로 하면 화면에는 `예정 3회분 · 만들 양 4회분 · 예상 여유 1회분`을 보여준다. 예상 여유는 실제 재고와 구분하고, 조리 완료 때 실제 만든 양을 확인한 후 재고를 늘린다.

- `1회분`은 해당 레시피의 기준 분량이다. 음식마다 동일한 g을 뜻하지 않으며, 기준 중량을 알면 함께 표시한다.
- 필요한 조리량은 예정 제공량에서 해당 날짜에 사용 가능한 기존 재고를 뺀 값으로 제안한다.
- 적게 만들기로 바꾸면 영향받는 끼니에 부족분을 표시하고 추가 조리·메뉴 교체로 해결하게 한다.
- 모아서 준비할 때 조리일 이후에 먹는 일정과 보관 가능 기간을 함께 확인한다. 한 번 만든 음식을 일주일 내내 냉장해도 된다고 가정하지 않는다.
- 장보기 합계는 **실제로 만들 조리 묶음의 재료량**에서 구한다. 같은 조리 묶음이 세 끼에 배치됐다고 재료를 세 번 합산하지 않는다.
- 원재료 보유 수량이 없으면 `보유 중·필요량 확인`으로 표시한다. 보유 여부만으로 필요한 장보기 수량을 0으로 만들지 않는다.
- 단위 변환 근거가 없는 개·g·ml, `약간` 항목은 강제로 합산하지 않는다. 계산용 값은 정밀도를 유지하고 최종 표시 단계에서 반올림한다.

## 7. 식사·간식 재고

`만든 음식`에서 **식사 / 간식**, **냉장 / 냉동**으로 빠르게 필터링한다. 재고는 레시피별 총량만 저장하지 않고 같은 메뉴라도 조리일·보관 장소가 다르면 다른 묶음으로 관리한다.

카드 예시: `두부전 · 냉동 · 남은 4회분 · 식단에 예약 3회분 · 자유롭게 쓸 수 있는 양 1회분`.

| 사용자 행동 | 계획·재고 처리 |
|---|---|
| 초안 생성 | 예상 사용량만 계산, 실제 재고·예약 변경 없음 |
| 식단 확정 | 기존 재고를 예약하고 부족분은 조리 예정에 배정, 실물 수량 차감 없음 |
| 조리 완료 | 실제 만든 양으로 입고, 해당 조리 예정에 연결된 예약을 새 재고로 이전 |
| 식사 제공 | 제공한 회분만 출고하고 예약 해제; 먹은 양·평가는 기존 기록에 연결 |
| 다른 날로 이동 | 새 날짜의 보관 가능 여부를 확인한 뒤 예약 변경 |
| 식단에서 삭제 | 예약만 해제, 이미 만들어진 음식은 재고에 유지 |
| 폐기·기한 만료 | 폐기 기록 또는 사용 불가 상태; 사용할 수 없어진 양의 예약을 해제하고 영향을 받는 향후 끼니에 대체 필요 표시 |
| 수량 정정·되돌리기 | 기존 이력을 삭제하지 않고 보정 이력 추가; 예약과 충돌하면 조정 안내 |

**반만 먹어도 꺼내 제공한 1회분은 재고에서 1회분 출고**한다. 먹지 않은 절반을 자동 재입고하지 않는다. 단순히 지난 식사를 기록하는 경우에는 재고 연결을 선택하지 않았다면 차감하지 않는다. `식사 기록`과 `재고에서 꺼냄`을 두 번 눌러도 한 번만 출고돼야 한다.

레시피 상세에서 등록하면 이름·분류·기준 회분을 자동 입력한다. 이미 있는 음식은 수동으로 이름·회분·보관 위치·날짜를 등록할 수 있다. 레시피·성분을 알 수 없는 음식은 재고 수량 관리와 사용자의 직접 배치만 허용하고, 자동 영양 계산·알레르기 적합 판정은 보류한다.

보관 기한은 사용자가 확인한 날짜 또는 별도로 검토된 보관 규칙에서 가져온다. 기존 생성 레시피의 `storageInfo` 숫자만으로 안전한 기한을 보장하지 않는다. 기한이 없으면 `기한 확인 필요`로 표시하고 향후 날짜에 자동 배정하지 않는다. 냉동·해동·장소 이동은 이력으로 남기고 기한을 무조건 연장하지 않는다.

음식 재고는 계정 단위로 공유하고 식단은 아기별로 관리한다. 같은 계정의 다른 아기가 같은 재고를 중복 예약할 수 없게 하며, 각 아기에게 배치할 때 음식의 실제 재료·알레르기를 다시 확인한다. 다른 계정과의 가족 공유는 후속 범위다.

## 8. 구현 구조

### 데이터 모델 제안

아래는 개념 모델이다. 실제 Prisma 마이그레이션은 구현 단계에서 작성한다.

| 모델/확장 | 핵심 데이터·책임 |
|---|---|
| `MealPlan` | userId, babyId, startDate, 7일 기간, DRAFT/CONFIRMED/ARCHIVED, revision, preferencesSnapshot |
| `MealPlanPreference` | 아기별 재사용 조건: 끼니 패턴·간식 횟수·조리일·시간·우선순위·기피 재료 |
| `MealPlanSlot` | planId, 날짜, 끼니, slotIndex(간식 여러 번), HOME/EXTERNAL/SKIPPED, 유지 여부 |
| `MealPlanItem` | slotId, 레시피 또는 단순 식품 참조, 제공 회분/중량, 레시피 버전·분량·영양 스냅샷 |
| `CookingTask` | planId, recipeId, 조리일, plannedServings, actualServings, 상태, 완료 요청 식별자 |
| `PreparedFoodBatch` | userId, recipeId 또는 수동 이름, 식사/간식, 실제 재료·알레르기·분량 스냅샷, 조리·보관·기한 정보 |
| `FoodAllocation` | planItemId, 준비된 batch 또는 cookingTask 중 하나, 예약 회분, ACTIVE/RELEASED/FULFILLED |
| `FoodStockMovement` | batchId, 입고/제공/폐기/보정/이동, 회분 증감, 이벤트 연결, 중복 방지 키 |
| `IngredientNutrition` / `FoodCompositionRecord` | 공식 식품 코드, 생/조리 상태, 영양소별 nullable 값·단위, 자료 출처·버전·확인일 |
| `NutritionReference` | 연령 구간, 필요한 추가 구분, 영양소·기준 종류·값·단위, 기준 문헌·버전 |
| `Recipe` / `RecipeSource` 확장 | 메뉴 역할, 출처 확인 상태·증거·확인일, 영양 계산 버전·누락 정보 |
| `MealLog` 확장 | planItemId, 제공 이벤트 연결(선택), 실제 제공량과 먹은 양의 구분 |

단순 식품도 공식 식품 데이터에 연결하되, 식재료 사전의 알레르기·월령 조건을 적용한다. 기존 기록과 재고가 없는 사용자는 nullable 연결로 호환한다. 기존 PantryItem을 완성 음식 재고로 자동 변환하지 않는다.

식단의 날짜·끼니·slotIndex 중복을 제한하고, 겹치는 주간 식단의 같은 아기·같은 끼니를 확정할 때 충돌을 표시한다. 날짜는 KST 달력 날짜로 처리한다. 계정 소유권을 서버에서 검증하고 아기 전환 시 관련 데이터·캐시를 분리한다.

재고 입출고와 예약·식사 연결은 한 트랜잭션으로 처리한다. 잠금 또는 버전 비교로 동시 예약·차감을 방지하고, 요청 식별자로 재시도의 멱등성을 보장한다. `잔여 >= 0`, `활성 예약 합계 <= 사용 가능한 잔여`를 강제한다. 이미 다른 조리 묶음에 예약된 양은 새 식단에서 다시 사용할 수 없다.

### 코드 배치와 인터페이스

- 화면: `/meal-plan`, `/meal-plan/new`, `/meal-plan/[id]`, `/meal-plan/stock`. 상세 경로에는 소유권 검증을 적용한다.
- 도메인: `src/features/meal-plan`(생성·교체·확정), `nutrition`(정규화·계산·평가), `food-stock`(예약·입출고·보관), 기존 `serving`(분량 표시).
- 조회: `GET /api/meal-plans`, `GET /api/meal-plans/[id]`, `GET /api/food-stock`.
- 초안 생성: `POST /api/meal-plans`는 조건과 선택 재료를 받아 저장된 초안을 반환한다. 기존 초안을 덮어쓰지 않는다.
- 편집: `PATCH /api/meal-plans/[id]`와 항목 교체 API는 revision을 받으며 오래된 편집은 충돌로 돌려준다. 영양·조리량·예약 영향을 함께 재계산한다.
- 확정: `POST /api/meal-plans/[id]/confirm`에서 후보 안전 조건·재고·보관 기한·현재 프로필을 재검증한다.
- 조리 완료: `POST /api/cooking-tasks/[id]/complete`에서 실제 조리량과 재고 입고를 처리한다.
- 제공/폐기/수정: `POST /api/food-stock/[id]/movements`에서 이벤트를 기록하고, 제공에 연결된 기록은 기존 meal-log 서비스를 호출한다. UI가 별도로 이중 차감하지 않도록 공통 서비스로 묶는다.

계산 결과에는 사용한 레시피·영양 기준·생성 조건의 버전을 남긴다. 레시피가 변경되면 기존 계획의 영양값을 몰래 바꾸지 않고 변경됨을 안내한다. 알레르기 추가 등 안전 조건 변경은 즉시 향후 계획을 재점검하고 해당 항목을 교체 대상으로 표시한다.

## 9. 구현 순서와 완료 증거

기본 뼈대 → 기능 구현 → UI·접근성 → 요구사항·버그·엣지케이스 검토 순서로 진행한다. 모든 단계를 마친 뒤 전체 기능 완료로 판단한다.

| 단계 | 작업 | 완료 증거와 다음 단계 조건 |
|---|---|---|
| 기본 뼈대 | 식단·조리·재고·영양 모델, 화면 경로, 프로필 문맥, 문답 초안, 출처·영양 데이터 상태 정의 | 빈 식단 저장·조회와 아기별 분리 확인. 날짜/끼니/회분의 의미와 마이그레이션 호환 확인 후 진행 |
| 기능 구현 | 재료 기반 주간 조합, 메뉴 교체·유지, 영양 계산, 회분 조절, 장보기, 재고 입출고·예약, 먹은 기록 연결 | 재료 선택부터 식단 확정·조리·제공까지 연결된 시나리오와 수량 일관성 확인. 가상 출처 배제 및 영양 데이터 누락 처리 확인 |
| UI·접근성 | 짧은 문답, 모바일 하루 목록·주간 보기, 데스크톱 주간 표, 스테퍼, 상태·오류·빈 결과, 키보드 조작 | 작은 화면에서 가로 넘침 없이 사용, 색 이외 상태 구분, 초안 복원, 질문 반복 최소화 확인 |
| 요구사항·버그·엣지케이스 검토 | 아래 수용 기준과 동시성·권한·날짜·데이터 품질 확인 | 주요 시나리오의 자동 검증과 실제 화면 증거, 알려진 한계 기록 후 출시 판단 |

개발상 내부 배포는 수동 계획·조리량 → 재고 연결 → 자동 조합·영양 체크 순서로 나눌 수 있다. 다만 식품군 표시만 있는 상태를 요청한 정량 영양 체크의 완료로 간주하지 않는다.

| WP-01 | 재료 화면에서 주간 계획 시작 | 선택 재료가 전달되고 후보 선택에 실제 반영되며 부족한 재료가 표시됨 |
| WP-02 | 평일 점심 외부 식사, 간식 하루 2번 | 정확한 7일·끼니가 생성되고 외부 식사를 임의로 채우지 않음 |
| WP-03 | 선택 재료만으로 후보 부족 | 빈 칸·이유와 해결 선택지 표시; 출처 미확인 후보나 안전 조건 완화로 채우지 않음 |
| WP-04 | 특정 메뉴 유지 후 재추천 | 유지한 항목·사용자 수정량 보존, 나머지만 교체 |
| WP-05 | 3회분 예정에 4회분 조리 | 예상 여유 1회분, 조리 완료 전 입고 없음, 실제 완료량만 입고 |
| WP-06 | 냉동 음식 예약 후 다른 식단 생성 | 계정 전체에서 중복 예약되지 않으며 재고보다 많은 배정 차단 |
| WP-07 | 식단 삭제·이동·기한 경과 | 삭제는 예약만 해제; 이동은 새 날짜 검증; 사용할 수 없는 재고 연결은 대체 필요 표시 |
| WP-08 | 1회분 제공 후 반만 먹음, 재시도 | 출고는 한 번 1회분, 섭취 기록은 반; 재시도로 중복 기록·차감 없음 |
| WP-09 | 나트륨 외 영양소 누락, 약간 분량 | null을 0으로 계산하지 않고 항목별 평가 범위 표시; 완전한 영양 충족 판정 없음 |
| WP-10 | 외부 식사·우유 섭취 미입력 | 계획된 음식의 부분 추정임을 표시, 하루 전체 영양 부족으로 단정하지 않음 |
| WP-11 | 반찬·밥·간식 복합 구성, 같은 조리 묶음 재사용 | 끼니 영양은 실제 제공량을 합산, 장보기는 조리량 기준으로 한 번만 합산 |
| WP-12 | 알레르기 추가·아기 변경·다른 사용자 요청 | 향후 계획 재검증, 다른 계정 데이터 접근 차단, 재고별 적합성 재평가 |
| WP-13 | 5회분 초과 조리, 원재료 수량 미입력 | 별도 조리 묶음으로 분할; 보유 목록만으로 장보기 필요량을 0으로 만들지 않음 |
| WP-14 | 동시 편집·차감, 네트워크 재시도·오프라인 | 버전 충돌/멱등 처리, 온라인 반영 전 성공 확정 표시 없음, 음수 재고 없음 |
| WP-15 | 식단 기간 중 월령 구간 변경, 주 경계·지난 날짜 | 적용 날짜별 조건 점검; 지난 날은 새 자동 계획 대상에서 제외하거나 명시적으로 처리; KST 날짜 유지 |

계획 생성 성공률과 함께 문답 이탈, 첫 초안까지 걸린 시간, 사용자가 교체한 메뉴 비율, 실제 재고 사용·정정 비율을 관찰한다. 수치 목표는 초기 사용 결과를 보고 정한다.

## 11. 검토 범위

현재 소스·Prisma 스키마·PRD·UI 제안을 확인해 작성했다. 이번 검토에서 앱 코드나 DB는 수정하지 않았고, 런타임 동작·식품 데이터 적재·영양 수치의 정확성을 검증한 것은 아니다. 출처 문제는 앞선 DB 점검 결과를 전제로 반영했으며 이번에 DB 전수 재점검을 수행하지 않았다.

권장 첫 구현 범위는 7일 계획, 위의 문답, 재료 우선 구성, 메뉴별 조리 회분, 식사·간식 재고, 영양 체크와 데이터 품질 표시다. 자동 장보기 주문·가족 계정 공유·사진으로 음식 인식은 후속 범위로 둔다.
