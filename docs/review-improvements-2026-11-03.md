# 사용자 리뷰 기반 개선 검토서

검토일: 2026-11-03
대상: 재료 선택, 재료 기반 추천, AI 생성, 주간 식단, 음식 재고
상태: 구현 및 로컬 검증 완료. 운영 배포 최종 확인 예정.

## 1. 검토 결론

리뷰에는 실제 표시·매칭 결함과 생활 패턴을 표현하지 못하는 기능 공백이 함께 있다. 먼저 재료 탐색과 보유 재료 판정의 신뢰성을 고치고, 조리 주기를 선택하도록 확장한 다음, 끼니를 여러 요리로 구성하는 식단 유형을 도입한다. 데이터 확충은 단순 레시피 수가 아니라 사용자가 요청한 끼니 유형별 후보 수를 기준으로 진행한다.

## 2. 확인된 현행 동작

### 재료 목록과 두부·순두부

- `src/components/MealPlannerClient.tsx`: 재료를 검색하지 않으면 첫 40개, 검색하면 첫 80개만 렌더링한다. 목록 안의 스크롤만 있고 전체 항목을 추가로 불러오는 기능이 없다.
- `src/features/ingredient-search/index.ts`: 일반 재료 검색 응답은 최대 25개다. 이름순 목록의 뒷부분이 기본 목록에 드러나지 않을 수 있다.
- `src/app/api/ingredients/route.ts`: 알레르기 등록용 검색도 최대 25개다.
- 실제 사용자가 본 화면의 위치는 확인하지 못했으나, 'ㄷ에서 끊긴다'는 현상과 일치하는 표시 제한이 있다. DB 자체가 ㄷ 이후 재료를 갖고 있지 않다는 결론은 낼 수 없다.
- 재료 매칭은 `INGREDIENT_FAMILY_GROUPS`에서 두부와 순두부, 쌀밥과 백미, 육류의 여러 부위를 같은 보유 그룹으로 확장한다. 두부 선택만으로 순두부를 보유한 것으로 계산할 수 있으며, 부족 재료에서도 빠질 수 있다.

### 조리 주기

- 화면 선택지는 '매일 간단히 / 주 2회 모아서 / 상관없어요'다.
- 모아 만들기를 고른 뒤 실제 조리 날짜는 여러 개 선택할 수 있다. 현재 주 범위에서 첫날·4일째·7일째를 선택하면 3일 간격에 가까운 일정은 구성할 수 있다.
- '3일마다'라는 직접 선택과 다음 주까지 이어지는 반복 기준일은 없다.
- 현 엔진은 메뉴를 먼저 뽑고 각 식사의 이전 조리일을 찾는다. 조리 날짜를 줄여도 해당 날짜에 서로 다른 요리를 많이 만들게 될 수 있다. 날짜 설정만 추가해서는 조리 부담 문제가 완전히 해결되지 않는다.

### 메뉴 후보와 AI

- '추천 메뉴 찾기'는 DB의 활성 레시피를 조회하고 월령·간 단계·알레르기 조건을 적용한다. 선택 재료와 하나 이상 겹치는 레시피를 중심으로 일치율을 계산한다. 이 버튼은 AI를 실행하지 않는다.
- 'AI 새 레시피'는 별도 생성 요청이다. 선택한 보유 재료를 최대한 활용하도록 요청하지만, 선택한 재료만 사용하도록 강제하지는 않는다. 월령·알레르기 기준에 맞는 전체 허용 사전을 제공한다.
- AI의 허용 식재료 사전과 검증 기준, 검색된 참고 자료, 캐시 재사용이 생성 범위를 제한한다. 동일 조건의 유효한 캐시는 기존 결과를 반환한다.
- 주간 식단도 저장된 레시피를 사용한다. 출처 확인 여부, 월령, 간, 도구, 조리시간과 장보기 허용 여부 등이 후보를 줄인다.
- 장보기 미허용이면 모든 필수 재료가 선택 목록에 있어야 하는 강한 조건이다. 재료가 적으면 후보가 크게 줄 수 있다.

### 끼니 구성

- 주간 자동 생성은 식사 후보를 `MAIN` 역할로 제한하고 한 끼에 하나를 배치한다. `SIDE`와 `UNKNOWN`은 자동 후보에서 제외한다.
- DB와 서비스에는 같은 끼니에 여러 항목을 추가하고 순서를 갖는 기반이 있지만, 자동 생성은 끼니별 구성 규칙을 지원하지 않는다.
- 현재 '식사/간식', 'MAIN/SIDE/STAPLE'만으로는 스프, 한그릇 음식, 고기 반찬 등의 요구를 충분히 표현할 수 없다.

## 3. 개선안

### A. 재료 탐색 및 정확한 보유 판정 — 최우선

1. 재료 목록에 전체 검색 결과 수, 현재 표시 수, 더보기를 제공한다. 분류 필터(채소·육류·생선·두부 등)와 가나다 이동을 선택적으로 제공한다.
2. 인기 재료와 전체 재료 탐색을 구분하며, 검색·더보기 후에도 선택 상태를 유지한다.
3. 동일 재료의 다른 이름(계란/달걀)만 같은 보유 재료로 취급한다.
4. 두부/순두부, 생쌀/쌀밥, 서로 다른 고기 부위는 별도 재료로 유지한다. 대체 가능성은 보유 여부와 분리한다.
5. 대체 재료를 허용할 때는 '두부 보유 · 이 레시피는 순두부 필요'와 차이를 표시한다. 조리법·분량·식감 조정이 확인된 경우에만 대체 안내를 제공한다. 자동으로 '모든 재료 보유'라고 표시하지 않는다.
6. 추가할 재료가 검색되지 않을 경우에는 '재료 요청'으로 수집한다. 검증되지 않은 자유 입력 재료를 곧바로 자동 식단이나 AI 허용 사전에 넣지 않는다.

완료 기준:
- 이름순 뒤쪽 재료도 검색 없이 더보기로 도달할 수 있다.
- 두부만 선택하면 순두부는 보유로 계산되지 않는다.
- 쌀밥과 백미도 서로 자동 보유 처리하지 않는다.
- 동일 이름·동의어는 중복 선택되지 않으며, 알레르기 제외는 모든 페이지와 검색에서 유지된다.

### B. 3일마다 만들기 — 조리 일정과 메뉴 재사용을 함께 설계

질문: '음식은 얼마나 자주 준비하나요?'
선택지: 매일 / 2일마다 / 3일마다 / 직접 날짜 선택

- 시작 기준일에서 연속 날짜 간격으로 계산한다. 3일마다라면 시작일, +3일, +6일에 조리한다. 다음 주도 직전 기준일을 이어 계산한다.
- '3일마다 조리'와 '같은 메뉴를 며칠 먹어도 되는지'는 별도 설정이다. 상세 옵션으로 '다양하게 / 2~3일 나눠 먹어도 좋아요'를 제공한다.
- 먼저 조리 구간을 만들고, 그 구간에 재사용 가능한 요리와 이미 만들어 둔 음식을 배치한다. 같은 요리는 필요한 회분을 합산해 하나의 조리 작업으로 묶는다.
- 사용자에게 조리일마다 요리 종류 수·총 회분·예상 시간을 먼저 보여준다. 메뉴가 너무 많으면 간소화 대안을 제시한다.
- 조리일과 섭취일, 보관 장소·기한을 별도로 관리한다. '3일마다 조리'를 '모든 음식을 냉장 3일 보관 가능'으로 취급하지 않는다. 사용 기한 안에 배치할 수 없는 음식은 냉동 가능 여부를 확인하거나 조리일·메뉴를 조정한다.

완료 기준:
- 주가 바뀌어도 조리 간격이 끊기지 않는다.
- 식단에서 같은 요리를 여러 번 먹으면 합산 회분과 재고 예약이 일치한다.
- 날짜 변경·메뉴 교체 시 조리 작업과 재고 예약이 함께 갱신된다.

### C. 메뉴가 적은 이유를 설명하고 탐색 범위를 선택

추천 결과에는 필요한 경우에만 '왜 적게 나오나요?'를 제공한다. 서버가 실제 계산한 단계별 후보 수와 제외 사유를 보여준다. 표시 예시의 개수는 실제 계산값만 사용한다.

검색 범위 선택:
- '있는 재료로 만들기': 선택 재료와 사용자가 확인한 기본 재료 안에서 구성.
- '조금 더 사도 좋아요': 보유 재료를 우선 사용하며 부족 재료를 명확히 표시. 추가 재료 상한은 간단한 옵션으로 설정.
- '새 메뉴 찾아보기': 월령·알레르기 기준에 맞는 전체 저장 레시피를 탐색. 보유 재료 겹침을 필수 조건으로 두지 않음.

DB 추천과 AI 생성은 결과와 행동 이름에서 구분한다. 예: '저장된 레시피에서 찾기', 'AI로 새 레시피 만들기'.

AI 생성 요청에도 같은 범위·추가 재료 허용 수·원하는 요리 유형을 전달한다. 서버 검증에서 선택 재료 활용과 추가 필수 재료 수를 확인하고, 결과에 실제 보유·추가 구매·대체 필요를 따로 표시한다. 캐시 키에도 범위와 요리 유형을 포함한다. '다른 메뉴 생성'은 기존 캐시와 별도 선택으로 제공하고 한도 적용을 명확히 안내한다.

DB 확충 기준:
- 월령 × 간 단계 × 식사 유형 × 주재료 × 출처 확인 여부별 후보 수를 집계한다.
- 이름만 바꾼 중복 레시피 수를 늘리지 않는다.
- 스프·한그릇·고기 반찬·채소 반찬·밥 등 부족한 유형부터 실제 출처와 조리 내용을 확인해 보완한다.
- 후보가 없으면 사용자가 고른 유형을 알리지 않고 임의의 다른 음식으로 바꾸지 않는다.

완료 기준:
- 사용자가 현재 결과가 저장 메뉴인지 AI 생성인지 알 수 있다.
- 후보 부족이 데이터 부족인지 재료·조건 제한인지 구분할 수 있다.
- 알레르기·월령 등 안전 조건을 완화해서 개수를 늘리지 않는다.

### D. 끼니별 식단 유형 — 복수 요리 구성

간단 질문: '평소 한 끼를 어떻게 차리나요?'
아침 / 점심 / 저녁 행마다 유형을 선택하고, 처음 한 번 저장해 다음 식단에 재사용한다.

- 스프류
- 한그릇 음식
- 밥 + 반찬
- 자유 추천

이번 리뷰의 저장 예시:
- 아침: 스프류
- 점심: 한그릇 음식
- 저녁: 밥 + 반찬 총 3~4개, 그중 고기 반찬 최소 1개

'고기 반찬 포함 3~4개'는 밥을 제외한 반찬 총개수로 명시한다. 스프 유형 선택만으로 스프 한 가지가 완전한 한 끼 영양을 충족한다고 판단하지 않는다. 부족한 구성은 사용자가 추가할 수 있도록 안내한다.

데이터 구조:
- 한 끼(meal) 아래에 여러 요리(component)를 둔다. 기존 같은 날짜·끼니의 position 기반 항목을 활용하되, 자동 생성·교체·기록·재고 처리가 같은 묶음을 따르도록 보완한다.
- 요리 역할(주식/메인/반찬/간식), 형태(스프/죽/덮밥/볶음 등), 단백질 원재료(육류/생선/달걀/콩)를 구분한다.
- 고기 반찬 조건을 단순 단백질 점수로 대체하지 않는다. 콩·달걀이 육류 필수 조건을 충족하는 것으로 처리하지 않는다.
- 스프/반찬 여부를 메뉴 이름의 키워드만으로 확정하지 않고 DB를 검토·분류한다.
- 미분류 항목은 해당 유형 자동 구성에서 제외하고 보완 대상으로 집계한다.

구성 로직:
1. 각 끼니 유형에 필요한 역할과 개수를 만든다.
2. 프로필 안전 조건, 출처·자료 확인, 재료 선호, 조리 일정에 맞는 후보를 고른다.
3. 밥·고기 반찬·다른 반찬을 함께 구성하고 동일 끼니 중복을 방지한다.
4. 요리별 먹는 양과 만드는 양을 별도로 계산한다. 반찬 4개를 각각 기존 한 끼 분량 1회분으로 더하지 않는다.
5. 하루 영양은 실제 섭취 예정량을 합산하고, 미확인 성분은 부족 확정·충족 확정으로 표시하지 않는다.
6. '한 끼 전체 변경 / 이 반찬만 변경 / 이 반찬 고정'을 제공한다.
7. 기록은 한 끼에서 시작해 요리별 섭취량을 선택적으로 수정한다. 음식 재고는 각 요리별 실제 제공량을 차감한다.

화면 길이:
- 주간 화면에는 '저녁 · 밥 + 반찬 4'와 대표 이름만 표시한다.
- 상세 펼침에서 밥·반찬별 메뉴, 양, 교체 기능을 보여준다.
- 영양·장보기·조리 계획도 선택한 끼니 묶음을 기준으로 연결한다.

완료 기준:
- 아침·점심·저녁이 저장한 유형대로 구성된다.
- 저녁에 밥과 반찬 총 3~4개가 생성되고 그중 육류 반찬이 최소 1개다.
- 한 반찬을 바꿔도 나머지 고정 메뉴는 유지된다.
- 반찬별 섭취량·조리 회분·영양 합계·재고 차감이 일치한다.

## 4. 권장 진행 순서

1. 재료 더보기·검색과 잘못된 동등 매칭 수정. 추천 결과 설명을 함께 보완한다.
2. 3일 간격 조리와 조리 구간 단위 회분 합산·재고 재사용을 구현한다.
3. 끼니별 유형 및 역할·형태 분류를 도입하고, 유형별 후보 부족을 집계한다.
4. 밥+복수 반찬 자동 구성과 제공량·영양·재고·기록을 연결한다.
5. 부족한 유형의 검증 가능한 레시피를 확충하고 AI 생성에도 동일한 요청 유형을 전달한다.

각 작업은 기본 뼈대 → 기능 구현 → UI·접근성 → 요구사항·버그·엣지케이스 검토 순서로 진행한다. 특히 복수 반찬은 메뉴를 화면에 여러 개 나열하는 것으로 완료하지 않고, 제공량과 재고 계산까지 연결된 상태를 완료 기준으로 삼는다.


## 5. 구현 결과

- 재료 목록·검색 상한을 제거하고 화면에서 40개 단위 더보기 제공. 선택 상태 유지 및 미등록 재료 요청 저장.
- 두부/순두부, 생쌀/쌀밥, 고기 부위를 자동 동등 보유 처리하던 확장 제거.
- 저장 메뉴의 검색 범위 3종과 추가 필수 재료 수 설정, 실제 후보 수 기반 진단 표시.
- AI 생성에도 범위·추가 재료 수·요리 형태를 전달하고 서버 검증. 유형과 범위를 캐시 키에 포함하며 다른 메뉴 생성 선택 지원.
- 2/3일 간격·반복 기준일·메뉴 반복 허용 및 직접 조리일 선택 지원.
- 아침·점심·저녁 유형, 반찬 3/4개·고기 포함·반찬별 부분 회분 설정 지원. 보관한 식단의 설정은 다음 계획에 재사용.
- 한 끼/반찬 개별 교체, 개별 유지, 한 끼 기록과 요리별 섭취량·반응 입력 지원.
- 부분 회분을 식단·조리 작업·예약·재고·영양·장보기에서 일관되게 처리. 기존 정수 수량은 그대로 보존하는 Float 전환 마이그레이션.
- 기존 레시피의 유형 분류 목록과 스프 3개·반찬 6개 응용 레시피 추가. 실제 확인된 기존 원문의 재료 조합을 참고하며 원문과 조리 형태·분량이 같다는 의미가 아님. 의료·영양 전문가 검수 완료로 표시하지 않음.
- 주간 화면은 끼니별, 조리 목록은 날짜별 접기. 영양 정보는 필요할 때 펼침.
